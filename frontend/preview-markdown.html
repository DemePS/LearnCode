Why this component comes first

Every other part of changelogd is built on one question: "what did git say?" If that one call is sloppy, the bugs show up later as mysterious empty results or mojibake in the middle of your release notes, and you'll waste an hour debugging the wrong layer.

So before we do anything interesting, we make a boring, trustworthy function that runs git and hands back its output.

The four traps in subprocess.run(["git", ...])

Each of these is a real bug people ship:

  1. The pager. If core.pager is set (many people run delta or less), git may write to a pager instead of stdout. --no-pager at the front of the argv kills that.
  2. User config. A developer with alias.lg in their ~/.gitconfig changes your output. -c flags passed before the subcommand force the settings you depend on.
  3. The working directory. Never rely on the process's cwd. Pass cwd= explicitly so the runner works on any repo path.
  4. Failures that look like success. subprocess.run does not raise on a non-zero exit code.

Acceptance criteria

  • Runs a git command and returns str
  • Raises a dedicated exception on failure
  • Never invokes a pager

Pass cwd= rather than calling os.chdir() — that is global mutable state.

A fenced block, which the agent uses for the code it wants you to read:

def run_git(args: list[str], cwd: Path) -> str:
    proc = subprocess.run(
        ["git", "--no-pager", *args],
        cwd=cwd, capture_output=True, text=True,
    )
    if proc.returncode != 0:
        raise GitError(proc.stderr.strip())
    return proc.stdout

See the git documentation for the full list of environment variables.
